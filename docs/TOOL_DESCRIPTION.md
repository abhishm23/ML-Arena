# ML Arena — Tool Description

Version 1.0.0 · Local-first, no cloud, no LLM

---

## 1. Overview

**ML Arena** is a local desktop-class web application that lets people who have never
trained a model get a machine-learning answer out of their own spreadsheet.

**Name:** ML Arena · **Tagline:** *"Where models compete. You just pick the goal."*
**Source:** `C:\ML Arena` · **Language:** Python 3.11 backend, vanilla HTML/CSS/JS frontend

**Core purpose.** It replaces the usual "ask a data scientist" step. A user uploads a
file, picks a business question in plain English, points at the columns they care about,
and the tool runs a competitive field of models on the data, picks a winner, scores
every row, and produces an executive-ready report.

**Everything runs on the user's own machine.** There is no API key, no account, no
upload, and — deliberately — **no LLM anywhere in the product**. Every sentence shown
to the user is generated by deterministic rules from the actual computed numbers.

**Who it is for:**

| Audience | What they get |
|---|---|
| Business / finance / commercial analysts who cannot code | A way to run real ML without learning sklearn or hiring anyone |
| Small and mid-size teams without a data-science function | Access to modelling that is normally commissioned from a consultant |
| Data scientists | A fast first-pass baseline and a defensible model comparison, before deeper custom work |
| Anyone with sensitive data | Analysis that never leaves the machine — a compliance property, not a setting |

## 2. Capabilities

### 2.1 Nine built-in business questions

Each is a recurring real-world question, not a generic "predict this column":

| Key | Task | Sector | Primary metric | What it does |
|---|---|---|---|---|
| `discount_leakage` | Classification | Sales | ROC-AUC | Learns the discount a row *should* have got from its context; flags rows far above their own expectation |
| `margin_overflow` | Classification | Finance | ROC-AUC | Flags orders falling below the margin policy implied for their segment |
| `revenue_predict` | Regression | Sales | R² | Predicts a money column and ranks what drives it |
| `demand_forecast` | Regression | Operations | R² | Time-aware forecast with lag/rolling/calendar features, against a seasonal-naive baseline |
| `churn_risk` | Classification | Customer | ROC-AUC | Aggregates to customer level; scores who is about to stop buying |
| `credit_default` | Classification | Risk | ROC-AUC | Probability of default, translated to expected loss |
| `transaction_anomaly` | Anomaly (unsupervised) | Risk | Consensus | Finds records that do not look like the others; needs no labels |
| `segmentation` | Clustering | Customer | Silhouette | Groups customers/products into behavioural segments and describes each |
| `price_elasticity` | Regression | Sales | R² | How demand responds to price; the revenue-maximising discount |

### 2.2 The model race

A field of models is assembled from scikit-learn, XGBoost and LightGBM, spanning
genuinely different ways of thinking:

- **Classification (11):** logistic, decision_tree, random_forest, extra_trees, hist_gb,
  gradient_boosting, xgboost, lightgbm, knn, naive_bayes, mlp
- **Regression (14):** linear, ridge, lasso, elasticnet, decision_tree, random_forest,
  extra_trees, hist_gb, gradient_boosting, xgboost, lightgbm, knn, mlp, seasonal_naive
- **Anomaly (5):** isolation_forest, robust_zscore, lof, one_class_svm, elliptic_envelope
- **Clustering (6):** kmeans, minibatch_kmeans, bisecting_kmeans, gaussian_mixture,
  agglomerative, dbscan

**A failing model never kills the run.** Each is trained in its own try/except; a
failure is recorded in the leaderboard with `status="failed"` plus a plain-language
reason, and the race continues.

### 2.3 The custom-column builder

Users can create a column from existing ones with a live-preview formula engine:
**18 functions** (`abs, round, min, max, sqrt, log, log10, exp, clip, floor, ceil,
ifelse, coalesce, year, month, day, days_between, isnull`) and **16 operators**.

```
(list_price - net_price) / list_price     -> discount_pct
( revenue   - cost     ) / revenue        -> gross_margin_pct
ifelse(margin < 0, 1, 0)                  -> is_loss_making
```

The tool also **suggests** these automatically by reading column names, and will not
re-suggest a column the file already has.

**Security:** formulas are never passed to `eval`. The expression is parsed into an AST
and every node checked against a strict whitelist; attribute access, subscripts,
comprehensions, lambdas and imports are refused with a readable message. The validated
tree compiles to a **vectorised Polars expression**. A test asserts
`__import__('os').system(...)` is rejected.

### 2.4 "Why was this row flagged?"

For each of the worst-scoring records, the tool explains the decision in a sentence the
user can verify against the record:

> **ORD-2024-016787 · 2024-07-24** — score 0.99
> Its `discount_pct` was **49.1%**, where a typical record is **17.7%**. On its own that
> pushed this row's score up by 0.90.

Method: **model-agnostic single-feature ablation** — swap one column for the value a
typical record has, predict, measure how far the score moves. Chosen over SHAP because
it needs no extra dependency, works for every estimator in the zoo (including those
exposing no `coef_`/`feature_importances_`), and yields a sentence verifiable by eye.
All variants batch into one predict call. Percent-like columns are detected and
rendered as percentages (49.1%, not 0.4909).

### 2.5 Live narration

Progress streams over a WebSocket as structured events (`phase, level, title, detail,
progress, model, metrics, payload`). Each event carries a plain-language explanation of
*what* is happening and *why*. Every model gets a memorable persona — e.g. Random
Forest is "The Committee of Experts", XGBoost is "The Championship Booster",
Isolation Forest is "The Odd-One-Out Spotter".

### 2.6 Measurement discipline

Two properties are enforced, because a flattering number is worse than no number:

- **Test split and full file are never blended.** Top-level metrics (`precision`,
  `recall`, `f1`, `roc_auc`) are computed on held-back test rows at the chosen cut-off;
  the whole-file view lives only under `all_rows`.
- **Realistic cut-offs.** A 0.50 probability threshold is meaningless for a rare event.
  The tool agrees a **review budget** instead and reports the actionable number:
  *"reviewing the top 600 rows catches 63% of the problem; those rows are 12.7× more
  likely to be real."*

### 2.7 Performance

| Technique | Measured effect |
|---|---|
| Polars columnar engine + PyArrow | 1M-row CSV loads in ~40 ms; sampled profiling ~50 ms |
| Lazy scanning + sampling on very large files | Multi-GB files stay responsive |
| Train on a sample, score every row (>400k rows) | Bounded training time, full coverage |
| Budget-aware model pool | Heavy models dropped when the clock/data is against them |
| Batched scoring | No end-of-run memory spike |
| CPU-first tuning | No GPU required or expected; thread usage tuned to the machine |

**Reference run:** 60,042 rows × 20 columns → 10 models raced, ~85 s total, file read
in ~50 ms.

### 2.8 Exports

- **HTML report** — one self-contained file, inline styles and inline SVG charts, no
  CDN or external fonts; opens offline. Reference size **74 KB**.
- **CSV** — every scored row, UTF-8 with BOM so Excel opens it cleanly.
- **Excel** — 5 sheets: Summary, Model Leaderboard, Key Drivers, Insights, Scored Data.
- **JSON** — machine-readable summary.

### 2.9 Limitations and requirements

**Requirements:** Python 3.11+; ~1 GB with the venv and dependencies; ~124 MB for the
bundled samples (94 MB of that is one large benchmark file). No GPU needed.

**Limitations (documented in the README rather than hidden):**
- No deep learning — no PyTorch/TensorFlow; gradient-boosted trees are the correct
  choice for tabular business data on CPU, and a neural network still competes and
  loses on its merits.
- Correlation, not causation; the narration says so.
- Discount-leakage detection depends on the user supplying context columns.
- Row explanations are single-feature ablation, which overstates correlated columns.
  Stated in the UI and report, not hidden.
- XGBoost/LightGBM use fixed round counts rather than early stopping.
- Currency is never asserted: the file's currency is unknowable, so figures read
  "3.53 billion", never "$" or "₹".

## 3. Usage

### 3.1 Installation

```bash
cd "C:\ML Arena"
python -m venv .venv
.venv\Scripts\activate
pip install -r requirements.txt
```

Dependencies: polars, pyarrow, pandas, numpy, scikit-learn, xgboost, lightgbm, scipy,
openpyxl, fastapi, uvicorn, python-multipart, websockets.

### 3.2 Running

```bash
python run.py                 # opens http://127.0.0.1:8765
python run.py --port 9000     # choose a port
python run.py --no-browser    # start without opening a window
```

Or double-click **`start.bat`** (Windows). The launcher picks the next free port if the
default is taken, waits for the server to answer, then opens the browser. **Ctrl+C** stops it.

### 3.3 Typical workflow — six steps

| Step | Action |
|---|---|
| **1. Start** | Drop a CSV, Excel, Parquet or JSON file, or open a bundled sample. Machine capabilities are shown honestly (cores, memory, "CPU only"). |
| **2. Your data** | Shape, read time, engine used, a plain-language quality headline, and a column table badged *money / number / category / date / id / text*. Optionally build a custom column. |
| **3. The question** | Pick one of nine business questions, grouped by sector, each with a one-line story. |
| **4. The columns** | One picker per role. Each picker offers **only** columns of the right kind — the money slot shows money columns, the category slot shows categories. |
| **5. The arena** | Watch the live log, progress bar, and a model scoreboard that fills in as each model finishes. |
| **6. The answer** | Champion card, business impact, metric cards, charts, key drivers, insights, per-row explanations, flagged rows, and exports. |

**Inputs:** a tabular file (CSV/TSV/Excel/Parquet/JSON/NDJSON) and a column mapping.
**Outputs:** a scored dataset (every row, with its score) plus a report in HTML/CSV/XLSX/JSON.

### 3.4 API

16 REST endpoints and one WebSocket, for scripting or integration:

```
POST   /api/datasets                        upload a file
GET    /api/datasets/{id}                   dataset + profile
GET    /api/datasets/{id}/suggestions       auto-suggested derived columns
POST   /api/datasets/{id}/columns/preview   validate + preview a formula
POST   /api/datasets/{id}/columns/apply     create derived columns -> new dataset
GET    /api/usecases                        catalogue, functions, operators, metric glossary
POST   /api/runs                            start an analysis
GET    /api/runs/{id}                       status + full result
GET    /api/runs/{id}/export?fmt=...        html | csv | xlsx | json
GET    /api/samples                         bundled datasets
POST   /api/samples/{name}/load             load a bundled dataset
GET    /api/health                          capabilities
WS     /ws/runs/{run_id}                    live event stream
```

### 3.5 Testing

```bash
.venv\Scripts\python.exe -m pytest tests -q        # 44 unit tests
.venv\Scripts\python.exe tests\test_api.py         # 87 end-to-end checks
.venv\Scripts\python.exe tests\ui_walkthrough.py   # drives the real UI in Chrome
```

`ui_walkthrough.py` drives the actual interface in headless Chrome over the DevTools
Protocol — clicking the sample card, mapping columns, pressing run — and screenshots
every step into `shots/`. It needs Chrome at the default Windows path and a server
already running on port 8770.

### 3.6 Extending

- **New business question:** add an entry to `usecases/registry.py` and a target branch
  in `usecases/definitions.py`. The UI picks it up automatically.
- **New model:** add a `ModelSpec` to `engine/models.py` with a persona and honest
  `cost` so the budget planner can drop it on big data.

`docs/CONTRACT.md` fixes the interfaces between layers.

## 4. Business value

### The problem

Organisations routinely commission a data scientist to answer a single commercial
question — *"where is discount leaking?"*, *"which customers are about to leave?"* —
because the people who understand the business cannot run the models themselves. That
creates three costs: a queue (weeks of waiting), a translation gap (the analyst does not
know which columns matter), and a delivery gap (the answer comes back as a model
artefact, not something a commercial team can act on).

Simultaneously, generic AutoML tools solve this only for people who already know what
ROC-AUC means. They optimise a metric and stop.

### How ML Arena solves it

1. **Removes the technical vocabulary.** The user picks a *question*, not an algorithm:
   "Discount leakage", not "gradient boosting classifier". Every metric is labelled in
   plain English ("separation power", not ROC-AUC) with a gloss in the same sentence.
2. **Automates the judgement calls a data scientist would make.** It reads the file in
   the fastest available engine, classifies columns into money/number/category/date/id,
   derives missing columns (list price minus net price = discount), chooses a test
   strategy, picks a realistic decision cut-off, and selects a winner — explaining each
   choice as it goes.
3. **Competes models instead of trusting one.** Nine to fourteen models race on identical
   data; the champion is chosen on held-out performance, and the runner-up and trade-off
   are reported alongside it, so the answer carries its own evidence.
4. **Closes the loop to action.** It does not stop at a ranked list — it says *which rows
   to review first*, *how many to review*, *what proportion of the problem that catches*,
   and *why each individual row* is on the list.

### Tangible benefits

| Benefit | Evidence |
|---|---|
| No data-science queue | Nine commercial questions answered without writing code |
| No data leaves the machine | Zero network calls anywhere in the application |
| Answers arrive in minutes | Reference run: 60k rows, 10 models, ~85 s end to end |
| Large files are not a blocker | 1M-row CSV read in ~40 ms; sampling keeps training bounded |
| Output is directly usable | Self-contained 74 KB HTML report, plus CSV/XLSX for follow-on work |
| The result is defensible | Model leaderboard, held-out metrics, champion rationale, row-level reasons |

### Representative use cases

1. **Margin protection (sales/finance).** Upload order-level data, run *Discount
   leakage*. The tool learns the expected discount per context and flags exceptions.
   On the bundled sample: 2,912 of 60,042 rows flagged, carrying **3.53 billion** in
   discount value; reviewing the top 600 catches 63% of the problem, and flagged rows
   are 12.7× more likely to be real. Drivers pointed at leaky sales reps and regions —
   the actionable finding.
2. **Churn containment (customer/subscription).** Run *Churn risk* on a customer
   extract to get a risk score per customer plus the revenue at stake, prioritised.
3. **Credit/risk triage (lending).** Run *Credit default* for probability of default
   translated into expected loss, with the drivers behind each decision.
4. **Fraud and error hunting (finance ops).** Run *Transaction anomaly* when there are
   **no labels at all** — five unsupervised detectors vote, and a record several methods
   independently call odd is a genuinely odd record.
5. **Planning (demand/revenue).** Run *Demand forecast* or *Revenue prediction* against
   a hold-out set, with a seasonal-naive baseline in the field so accuracy claims stay
   honest.
6. **Pricing (commercial).** Run *Price elasticity* to see how demand responds to
   discount and where revenue peaks.

### What it is not

It is not a replacement for a bespoke, productionised model with monitoring and
retraining. It is a **first-pass analysis and triage tool**: it tells a business user
whether a signal exists, how strong it is, and where to look — in minutes, on their own
machine, without involving anyone else.
