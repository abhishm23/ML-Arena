# ML Arena

**Where models compete. You just pick the goal.**

ML Arena is a local application that lets someone who has never heard the word
"hyperparameter" get a real machine-learning answer out of their own spreadsheet.

You upload a file. You pick a business question in plain English. You point at the
columns you care about. A field of models races on your data while a live,
plain-language log explains what each one is doing and why. The winner is used to
score every row, and you walk away with an executive-ready report.

**Everything runs on your own computer.** No account, no upload, no API key, no
cloud service, and — deliberately — **no LLM anywhere in the product**. Every
sentence you read is generated by deterministic rules from the actual numbers.

---

## Quick start

```bash
cd "C:\ML Arena"
python run.py
```

The browser opens at `http://127.0.0.1:8765`. If that port is busy, the next free
one is used automatically.

```bash
python run.py --port 9000      # pick a port
python run.py --no-browser     # start without opening a window
```

On Windows you can also just double-click **`start.bat`**.

### First run (setting up the environment)

ML Arena needs Python 3.11+ and the packages in `requirements.txt`:

```bash
python -m venv .venv
.venv\Scripts\activate
pip install -r requirements.txt
```

Then launch it. Nothing else to configure.

### Try it in 30 seconds

1. On the start screen, click the sample **`orders_discount_leakage.csv`**.
2. Choose **"Discount leakage"**.
3. Map the columns (the pickers only offer columns that make sense for each slot —
   money slots show money columns, category slots show categories).
4. Press run and watch the arena.
5. Export the HTML report.

| Step | What happens |

| **5. The arena** | Live narration log, overall progress, and a model scoreboard that fills in as each model finishes. |

## The nine business questions

| Question | Type | What it actually does |
|---|---|---|
| **Discount leakage** | Classification | Learns the discount a row *should* have got from its context, then flags rows far above their own expectation. |
| **Margin overflow** | Classification | Same idea applied to margin — flags orders that fall below the margin policy for their segment. |
| **Revenue prediction** | Regression | Predicts a money column from everything else, and ranks what drives it. |
| **Demand forecast** | Regression | Time-aware forecast with lag, rolling and calendar features, against a "same time last year" baseline. |
| **Churn risk** | Classification | Aggregates to customer level and scores who is about to stop buying. |
| **Credit default** | Classification | Probability of default, translated into expected loss. |
| **Transaction anomalies** | Anomaly (unsupervised) | Finds records that simply do not look like the others. No labels needed. |
| **Segmentation** | Clustering | Groups customers or products into behavioural segments and describes each one. |
| **Price elasticity** | Regression | How demand responds to price, and the discount that maximises revenue. |

Every one of these is a real, recurring question in finance, commercial and risk
teams. They are also all questions where a bespoke model is normally commissioned
from a data scientist — which is exactly the bottleneck this tool removes.

## How the engine works

### The race

For each question the engine assembles a field of models from scikit-learn,
XGBoost and LightGBM — typically 9–13 of them, spanning genuinely different ways
of thinking (linear, tree, ensemble, boosting, distance-based, probabilistic,
neural). Each gets the same training data and the same held-out test rows.

Every model is reported **even if it fails**. One bad model can never kill a run.

### Choosing the winner

- **Classification** — ranked by separation power (ROC-AUC), with PR-AUC,
  log-loss and Brier reported alongside.
- **Regression** — ranked by R², with MAE, RMSE, MAPE and WAPE.
- **Anomaly** — ranked by how much the detectors *agree*; a record that several
  independent methods call odd is a genuinely odd record.
- **Clustering** — ranked by silhouette and Davies-Bouldin, with the number of
  segments chosen from the data rather than hard-coded.

The champion then scores **every** row in your file, not just the test rows.

### Two numbers that are kept honest

The engine is careful never to blend the held-back test split with the whole file:

- **Top-level metrics** (`precision`, `recall`, `f1`, `roc_auc`) are computed on
  the held-back test rows at the exact cut-off that was chosen.
- **`all_rows`** is the same cut-off applied to your entire file.

Both are reported, clearly labelled, and they are never mixed into one confusion
matrix. That distinction matters: a number computed on rows the model has already
seen will always flatter it.

### Setting the cut-off like a human would

A 0.50 probability threshold is meaningless for a rare event — it can flag almost
nothing, or half your file. ML Arena instead agrees a **review budget** with you:
flag the riskiest slice of the file, which is what a person can actually work
through. It reports the genuinely useful number — *"reviewing the top 600 rows
catches 63% of the problem, and those rows are 12.7× more likely to be real"* —
rather than an abstract accuracy figure.

### "Why was *this* row flagged?"

A ranked list is only useful if you can act on it, and you cannot act on a number.
So for each of the worst records the report answers the obvious follow-up question,
in a sentence you can check against the record yourself:

> **ORD-2024-016787 · 2024-07-24** — score 0.99
> Its `discount_pct` was **49.1%**, where a typical record is **17.7%**. On its own
> that pushed this row's score up by 0.90.
> Its `gross_margin_pct` was **50.7%**, where a typical record is **43.9%**…

**How it works.** For one row, we swap a single column for the value a *typical*
record has and see how far the score moves. Whatever moves it most is what drove
that decision. We use this rather than SHAP because it needs no extra dependency,
works for every model in the zoo (including the ones with no coefficients or
importances at all), and produces a sentence a business user can verify by eye.

**Being honest about it.** Columns that overlap in meaning can each look important
on their own, so these are strong hints rather than an exact split of the blame —
and the report says so, in the same words, right under the list.

### Why it is fast

| Technique | Effect |
|---|---|
| **Polars** columnar engine (with PyArrow) for all reading and reshaping | A 1M-row CSV loads in ~40 ms; profiling sampled takes ~50 ms |
| **Lazy scanning + sampling** for very large files, with an honest note in the log | Multi-GB files stay responsive |
| **Train on a sample, score everything** — above 400k rows the models train on a stratified sample but still score every row | Bounded training time, full coverage of your data |
| **Budget-aware model pool** — heavy models are dropped when the clock or the data is against them | Runs always finish |
| **Batched scoring** | No memory spike at the end |
| **CPU-first design** | No GPU is required or expected; thread usage is tuned to the machine |

## The custom-column builder

The single most requested thing in tools like this: *"my file doesn't have a
discount column — can you make one?"*

Yes. Type a formula, see a live preview, and apply it. The original data is never
modified — you get a new dataset alongside it.

```
(list_price - net_price) / list_price        → discount_pct
revenue - cost                                → gross_profit
( revenue - cost ) / revenue                  → gross_margin_pct
quantity * unit_price                         → extended_value
ifelse(margin < 0, 1, 0)                      → is_loss_making
coalesce(discount_pct, 0) * revenue           → discount_value
round(amount, 2)                              → amount_rounded
days_between(ship_date, order_date)           → delivery_days
```

The tool also **suggests** these automatically by reading your column names — if it
sees `list_price` and `net_price`, it offers the discount derivation, and it will
not re-suggest a column you already have.

### It is safe by construction

Formulas are **never** passed to `eval`. The expression is parsed into an abstract
syntax tree and every node is checked against a strict whitelist; anything else —
attribute access, subscripts, comprehensions, lambdas, imports, calls to unknown
functions — is refused with a readable message. `__import__('os').system(...)` is
rejected, and there is a test that asserts exactly that. The validated tree is then
compiled into a **vectorised Polars expression**, so it runs at native speed rather
than row by row.

## Tests

```bash
.venv\Scripts\python.exe -m pytest tests -q          # all unit tests
.venv\Scripts\python.exe tests\test_api.py           # full end-to-end run
.venv\Scripts\python.exe tests\ui_walkthrough.py     # drive the real UI in Chrome
```

`test_api.py` drives the real server over HTTP and a real WebSocket: it loads a
sample, checks the column classification, builds a custom column, runs a complete
analysis, asserts the stream covers every phase, verifies the leaderboard,
champion and per-row explanations, and downloads all four export formats.

`ui_walkthrough.py` goes one further and drives the actual interface in headless
Chrome over the DevTools Protocol — clicking the sample card, choosing columns,
pressing run — then screenshots every step into `shots/`. It is the only check that
proves the interface, the API and the engine work together. It needs Chrome at the
default Windows path and a server already running on port 8770.

## Honest limitations

- **No deep learning.** There is no PyTorch or TensorFlow, and none is needed:
  on tabular business data, gradient-boosted trees reliably match or beat neural
  networks while training in seconds on a CPU. A neural network is still in the
  field, so it competes on equal terms and loses when it deserves to.
- **Correlation, not causation.** A driver ranking tells you what moves with the
  outcome, not what causes it. The narration says so.
- **Leakage detection depends on context columns.** If you give the discount model
  nothing but the discount, it cannot know what was reasonable. It says so in the
  log rather than inventing an answer.
- **Row explanations are hints, not an exact split.** Swapping one column at a time
  overstates correlated columns, because either one can carry the prediction alone.
  The report states this next to the explanations rather than letting them read as
  arithmetic.
- **XGBoost and LightGBM** use a fixed number of rounds rather than early stopping
  against a validation set, which leaves a little accuracy and time on the table.

A label column containing only one value now stops the run with a plain explanation
instead of racing models that cannot possibly learn anything.

## Extending it

**Add a business question** — add an entry to `usecases/registry.py` (name, story,
roles, task, metric) and a target-construction branch in `usecases/definitions.py`.
The UI picks it up automatically; no frontend change is needed.

**Add a model** — add a `ModelSpec` to `engine/models.py` with a persona and a
plain description. Give it an honest `cost` so the budget planner can drop it on
big data.

Both are additive: `docs/CONTRACT.md` fixes the interfaces between the layers.

## Where this could go next

Ordered by value-for-effort:

1. **Your own vocabulary.** Let a team rename "Discount leakage" to whatever they
   call it internally, and save that mapping. Adoption is a language problem.
2. **Compare runs.** Keep a history and diff two runs, so a user can prove the
   intervention worked. The run artefacts are already persisted per run id.
3. **Bring your own rule.** Let the user supply the definition of "bad" (a margin
   floor, a discount ceiling, a churn window) instead of the engine inferring it.
   That converts the tool from advisory to authoritative.
4. **Scheduled re-runs.** Point it at a folder that gets a new export every week and
   have it score the new file with the saved model, then email the delta.
5. **Model persistence.** Save a champion and reuse it to score tomorrow's file
   without retraining.
6. **Two-file mode.** Compare this month against last month directly.
7. **A PDF export** alongside the HTML report, for teams that circulate documents.
8. **Packaging.** Ship a single-file executable so no Python install is needed —
   the last real barrier to a non-technical user running this on their own laptop.

## Design principles

1. **The user is smart, just not a statistician.** Never dumb the maths down —
   translate it. "Separation power" is not a euphemism for ROC-AUC; it is what
   ROC-AUC means.
2. **Show your work.** Every number on screen traces back to a step in the log.
3. **Be honest about uncertainty.** Weak signals are reported as weak. Numbers from
   seen rows are never dressed up as out-of-sample performance.
4. **Never block the user.** No bare spinners; there is always a sentence saying
   what is happening.
5. **Local means local.** No network calls anywhere in the application.
